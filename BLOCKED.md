### Multi-character run support
- **Surface:** `src/Sts2Headless/HostMethods.cs:98-101` — `if (character != Character.Ironclad) throw new ArgumentException("...not yet supported (only Ironclad)")`. `Sts2Bindings.StartIroncladRun` is the only available entry point on the bindings layer.
- **Question:** Which characters to add and in what order (Silent / Defect / Watcher / Regent / Necrobinder), and whether `bindings.StartIroncladRun` should become `StartRun(character, …)` or a per-character family (`StartSilentRun`, …). Either shape needs character-specific starting decks, relics, and engine-side bootstrap differences.
- **Cheapest unblock:** Pick one new character (suggest Silent — closest to Ironclad in run shape) and confirm whether the bindings layer takes a character enum or stays per-character. Once decided, multi-character coverage in `CoverageSweepTests.s_runs` follows mechanically.
- **Discovered:** 2026-05-18 via fill-engine-gaps TODO scan (pass 1b) + coverage delta (pass 1c). The coverage report classifies ~80% of missing Cards/Relics/Powers as "off-class content the sweep cannot reach with single-character runs".

### Move-body patches that strip boss damage (Doormaker-shape audit)
- **Surface:** `src/Sts2Headless.Runtime/Patches/HangPatches.Monsters.cs` — the remaining monster patch entries pass move/lifecycle methods whose bodies still contain gameplay mutations.
- **Blast radius (2026-05-23, post-cleanup-3):** **1 patched method** still strips a gameplay mutator (down from 61 baseline 2026-05-21). The snapshot is locked into `tests/Sts2Headless.IntegrationTests/MonsterPatchAuditTests.cs` (`s_expectedDoormakerShape`). The remaining audit entry:
  - **Vantom.DismemberMove**: hang at round 3 after partial body execution (~40 HP damage lands, then combat wedges with `isPlayPhase=false`). Root NRE site partially identified — see "Vantom.DismemberMove deep-dive" sub-bullet below — but a single-patch fix is INSUFFICIENT.
    - **2026-05-23 investigation:** `--probe-method-body Vantom DismemberMove` shows IL 198-201 emits `call NGame.get_Instance; callvirt NGame.DoHitStop` with NO null-gate (unlike the preceding `ScreenShake` call at IL 138-151 which IS `dup; brtrue; pop; br` null-gated). `NGame.DoHitStop` is non-virtual instance, body is `ldarg.0; ldfld _HitStop; callvirt NHitStop.DoHitStop` — null receiver NREs on the first `ldfld`. Only three callers in sts2.dll (Vantom.DismemberMove, CeremonialBeast.PlowMove, MechaKnight.HeavyCleaveMove); the latter two are null-gated, so a leaf-helper patch (`PatchNGameDoHitStop` returning void via `SkipVoidPrefix`) is safe and matches the Doormaker recipe.
    - **However:** adding `PatchNGameDoHitStop` and dropping the Vantom monster strip does NOT fix the smoke A0 hang. With `PatchVantomDismemberMove` removed and `PatchNGameDoHitStop` applied, `IroncladAgent_RunsToTermination_Seed42` still fails at the exact same fingerprint: `room=BossRoom|hp=39/80|round=3|playPhase=False|enemies=[VANTOM:168/173+0|SLIPPERY_POWER:4/VULNERABLE_POWER:1]`. So there's at least one MORE unprotected NRE site downstream — most likely inside `CardPileCmd.AddToCombatAndPreview<Wound>` (state machine `<AddToCombatAndPreview>d__22`1`; cannot be probed via `PatchProcessor.GetCurrentInstructions` due to generic-state-machine limitation: throws `NotSupportedException: Specified method is not supported`).
    - **Distinguishing fact:** the encounter sweep with `MECHANIC_SWEEP_FOCUS_IDS=VANTOM_BOSS` passes even with Vantom unstrip'd because the sweep drives only 2 turns then `debug/kill_all_enemies` — Vantom's intent rotation (`InkBlot → InkyLance → Dismember → Prepare`) lands DismemberMove at round 3, so the sweep never executes it. A focused regression test that drives 12 rounds against `debug/start_combat("VANTOM_BOSS")` with a 999-HP Defend deck IS sufficient to reproduce the hang — `roundsCompleted=3, isPlayPhase=False` even with the partial DoHitStop fix.
    - **Next investigation step:** trace the post-`AttackCommand.Execute` path of DismemberMove's d__34 state machine. The remaining unprotected calls between IL 197 (Attack returned) and IL 243 (AddToCombatAndPreview<Wound>) are: IL 198-201 (DoHitStop — patched and still fails) and IL 202-236 (Cmd.Wait + awaiter unwind — already patched). The NRE has to be either inside `CardPileCmd.AddToCombatAndPreview<Wound>(IReadOnlyList<Creature>, …)`'s d__22 inner state machine OR in a downstream hook that fires asynchronously (e.g., `Hook.AfterCardChangedPiles`, `Hook.AfterCardAddedToPile`). TestSubject calls `AddToCombatAndPreview<Burn>` and works in headless, so the issue is likely Wound-specific or Vantom-target-specific (perhaps the engine's `Wound` model triggers a relic listener like LUCKY_FYSH that NREs on UI state).
    - **Try-and-revert candidates that did NOT help:** stripping just `NGame.DoHitStop` (this investigation). Untried: stripping `CardPileCmd.AddToCombatAndPreview<Wound>` directly (would silently strip Vantom's wound mechanic — same Doormaker-shape anti-pattern), or installing a stub for `NPlayerHand.Instance` / `NPlayerDeck.Instance` (the wound is added to one of the player's piles; a NRE on the pile-node lookup is plausible).
- **2026-05-23 cleanup waves:** Audit shrank 61 → 1 across three cleanup waves.
  - **Wave 1:** Dropped strips for 11 monsters after IL probing confirmed TestMode.IsOn=true + BootstrapSequence.SetTestMode covers their UI gating (BowlbugRock, CeremonialBeast, CorpseSlug, DecimillipedeSegment, GremlinMerc, TerrorEel, TestSubject, TheInsatiable, ThievingHopper; partial cleanups on LagavulinMatriarch / SoulNexus / Tunneler / SlumberingBeetle).
  - **Wave 2:** Crusher + Rocket fixed via `PatchKaiserCrabBossBackground` — `RuntimeHelpers.GetUninitializedObject(typeof(NKaiserCrabBossBackground))` allocates a stub, Harmony-patches every Task/void method on it to no-op, and `Crusher.get_Background` / `Rocket.get_Background` are patched to return the stub. Restores 5 attack moves + AfterAddedToRoom × 2 (commit `838bfe3`).
  - **Wave 3:** LagavulinMatriarch + SlumberingBeetle AfterAddedToRoom fixed via body-replacement — a Harmony prefix runs PlatingPower + the sleep power (AsleepPower / SlumberPower) via reflective `PowerCmd.Apply`, then skips the post-power UI VFX block (commit `7badffe`). - **Cheapest unblock (DONE 2026-05-21):** `MonsterPatchAuditor` + `MonsterPatchAuditTests`. Adding a new monster patch with gameplay-mutating moves fails the audit until either the leaf-helper fix is applied (Doormaker-style) or the line is added to the expected list with a written justification.

### Treasure room previewable pick/skip
- **Surface:** `src/Sts2Headless.Protocol/MethodCatalog.cs:69` — `run/leave_treasure_room` summary explicitly mentions a "future slice can split this into previewable pick/skip". Today the engine's `TreasureRoomRelicSynchronizer` auto-picks the single relic offering on entry; the wire method just exits to MapRoom.
- **Question:** Two-step shape — does it become `run/preview_treasure_room` (returns the relic offering) + `run/pick_treasure_room` (accept or skip), or a single `run/leave_treasure_room(skip: bool)` with the preview surfaced through the existing snapshot's `treasureRoom` block? The two-step preview is cleaner but adds a new method; the param-on-leave is non-breaking but less symmetric with merchant/event flows.
- **Cheapest unblock:** Confirm whether previewability is a CURRENT need (replay determinism? agent decision-making?) or speculative. If speculative, leave the catalog summary as-is and revisit when a caller surfaces.
