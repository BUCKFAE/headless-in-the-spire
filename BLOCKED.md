### Multi-character run support
- **Surface:** `src/Sts2Headless/HostMethods.cs:98-101` — `if (character != Character.Ironclad) throw new ArgumentException("...not yet supported (only Ironclad)")`. `Sts2Bindings.StartIroncladRun` is the only available entry point on the bindings layer.
- **Question:** Which characters to add and in what order (Silent / Defect / Watcher / Regent / Necrobinder), and whether `bindings.StartIroncladRun` should become `StartRun(character, …)` or a per-character family (`StartSilentRun`, …). Either shape needs character-specific starting decks, relics, and engine-side bootstrap differences.
- **Cheapest unblock:** Pick one new character (suggest Silent — closest to Ironclad in run shape) and confirm whether the bindings layer takes a character enum or stays per-character. Once decided, multi-character coverage in `CoverageSweepTests.s_runs` follows mechanically.
- **Discovered:** 2026-05-18 via fill-engine-gaps TODO scan (pass 1b) + coverage delta (pass 1c). The coverage report classifies ~80% of missing Cards/Relics/Powers as "off-class content the sweep cannot reach with single-character runs".

### Move-body patches that strip boss damage (Doormaker-shape audit)
- **Surface:** `src/Sts2Headless.Runtime/HangPatches.Monsters.cs` — 16 of the 17 active monster patch entries pass move/lifecycle methods whose bodies still contain gameplay mutations. The "skip body, return CompletedTask" prefix kills those bodies **including** their `DamageCmd.Attack`, `PowerCmd.Apply<T>`, `CreatureCmd.SetMaxAndCurrentHp`, `CreatureCmd.Heal`, etc. — the gameplay-state mutations the boss needs to actually fight. Doormaker was the loud failure (sentinel HP turned the strip into a deadlock); for normal-HP bosses the symptom is silent — combat still ends because the *player* deals damage, just against a neutered enemy that never attacks back.
- **Blast radius (quantified 2026-05-21):** `MonsterPatchAuditor` enumerates **61 patched methods** that strip at least one gameplay mutator. The full snapshot is locked into `tests/Sts2Headless.IntegrationTests/MonsterPatchAuditTests.cs` (`s_expectedDoormakerShape`). Highlights:
  - `TestSubject.Revive` strips `CreatureCmd.Heal` — Act 2 boss's second-life mechanic gone.
  - `TestSubject.RespawnMove` strips `PowerCmd.{Apply,Remove}` — phase-transition powers gone.
  - `*.AfterAddedToRoom` on TestSubject / Crusher / Rocket / LagavulinMatriarch / SlumberingBeetle strips initial-power application.
  - Every patched `*Move` body's `DamageCmd.Attack` is gone — bosses never deal direct damage in headless.
- **Question:** Worth fixing now, and in what order? Same downstream criterion as before: if headless win-rate / replay corpus / BattleAgent training is calibrated against these neutered bosses, prioritize bosses on the win path (TestSubject Act 2, LagavulinMatriarch, the elite bosses). If it's just smoke testing, the audit is the regression net and individual fixes can be opportunistic.
- **Cheapest unblock (DONE 2026-05-21):** `MonsterPatchAuditor` + `MonsterPatchAuditTests`. Adding a new monster patch with gameplay-mutating moves fails the audit until either the leaf-helper fix is applied (Doormaker-style) or the line is added to the expected list with a written justification. The leaf helpers are a small fixed set (`Cmd.Wait`, `Cmd.CustomScaledWait`, `*.UpdateVisual`, `TalkCmd.Play`, `NRunMusicController.*`) — most fixes just need a per-monster UI helper added.
- **Next unblock (PER MONSTER):** For each entry in `s_expectedDoormakerShape`: `just probe-method-body <Monster> <Move>` → identify the UI helpers actually called → add to `HangPatches.Async.cs` or `HangPatches.Monsters.cs` (leaf-helper patches) → drop the method from the monster's `_xEntry.MethodNames` → add a focused regression test along the lines of `DoormakerPhaseTransitionTests.cs` → remove the line from `s_expectedDoormakerShape`. Each fix is its own commit and may surface new `Godot.*` stub gaps (Doormaker needed `Sprite2D.Texture`).
- **Discovered:** 2026-05-21 during the Doormaker investigation; quantified later the same day via `MonsterPatchAuditor`.

### Treasure room previewable pick/skip
- **Surface:** `src/Sts2Headless.Protocol/MethodCatalog.cs:69` — `run/leave_treasure_room` summary explicitly mentions a "future slice can split this into previewable pick/skip". Today the engine's `TreasureRoomRelicSynchronizer` auto-picks the single relic offering on entry; the wire method just exits to MapRoom.
- **Question:** Two-step shape — does it become `run/preview_treasure_room` (returns the relic offering) + `run/pick_treasure_room` (accept or skip), or a single `run/leave_treasure_room(skip: bool)` with the preview surfaced through the existing snapshot's `treasureRoom` block? The two-step preview is cleaner but adds a new method; the param-on-leave is non-breaking but less symmetric with merchant/event flows.
- **Cheapest unblock:** Confirm whether previewability is a CURRENT need (replay determinism? agent decision-making?) or speculative. If speculative, leave the catalog summary as-is and revisit when a caller surfaces.
- **Discovered:** 2026-05-18 via fill-engine-gaps catalog scan (pass 1a).
